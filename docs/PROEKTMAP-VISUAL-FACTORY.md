Философия и концепция производственного контура
Версия 0.1
Дата: 2026-09-29

СТАТУС ДОКУМЕНТА

Это концептуальный документ для дальнейшей работы в Cursor с AI-агентами.
Он фиксирует философию, продуктовую модель, производственный процесс и идеи
интеграции с ProektMap. Это не окончательное техническое ТЗ: конкретную
архитектуру, структуру файлов, интерфейсы и этапы реализации агенты должны
исследовать и предложить отдельно, не нарушая зафиксированных принципов.

Главная мысль:

PROEKTMAP НЕ СТРОИТ ЕЩЕ ОДИН AI-КОНСТРУКТОР.
PROEKTMAP ПРОДАЕТ И ПЕРЕДАЕТ AI-АГЕНТАМ ВОСПРОИЗВОДИМЫЕ ВИЗУАЛЬНЫЕ РЕШЕНИЯ.

============================================================
1. ОСНОВНАЯ ИДЕЯ
============================================================

Мы хотим применить к ProektMap модель, близкую по духу к Aura: человек видит
визуальный результат, понимает, что хочет нечто подобное для своего проекта,
и получает возможность воспроизвести этот подход с собственным контентом.

Но наша цель — не сделать клон Aura и не конкурировать с Cursor, Claude Code,
Codex, Windsurf, Lovable или другими инструментами генерации.

Наша идея — создать слой между визуальным вдохновением и AI-разработкой.

Пользователь:
- находит визуал, который ему нравится;
- смотрит его на desktop и mobile;
- понимает, для каких задач он подходит;
- изучает краткое описание визуального языка;
- получает комплект инструкций для своего AI-агента;
- применяет его к собственному проекту, контенту и стеку.

Формула:

DONOR / REFERENCE
→ VISUAL DNA
→ VISUAL SOLUTION
→ AGENT PACKAGE
→ USER PROJECT

Пользователь покупает не чужой сайт и не набор строк промпта.
Он покупает способ получить определенный уровень и характер визуального
результата с помощью своего AI-агента.

============================================================
2. ЧТО ТАКОЕ VISUAL SOLUTION
============================================================

Visual Solution — самостоятельное визуальное решение, упакованное так, чтобы
AI-агент мог применить его к новому проекту, с другим содержанием и в другом
предметном контексте.

Это не просто шаблон, не готовый сайт для копирования и не один промпт.

В состав решения могут входить:
- визуальное направление и характер;
- layout и сетка;
- типографика и иерархия;
- ритм и spacing;
- цветовая система;
- принципы работы с изображениями;
- правила построения компонентов и секций;
- адаптивное поведение;
- анимации и взаимодействия;
- требования к контенту;
- implementation guidance;
- prompts и инструкции агенту;
- подходящие skills;
- рекомендации по MCP;
- референсные скриншоты;
- критерии качества и чек-лист проверки.

Главный товар — RECIPE, то есть воспроизводимый рецепт визуального результата.

============================================================
3. КАК ЭТО ВПИСЫВАЕТСЯ В PROEKTMAP
============================================================

Актуальный публичный раздел готовых решений:

https://proektmap.ru/resheniya

Не использовать старое название BLUEPRINT как основное название нового
пользовательского продукта. В этой концепции основная сущность называется
SOLUTION, а для визуального направления — VISUAL SOLUTION.

Не ломать существующую философию /resheniya. Новая функциональность должна
органично встроиться в действующий раздел, а не превращать его в отдельный
конструктор или изолированный маркетплейс.

На уровне концепции можно различать:

PRODUCT SOLUTION
Готовый маршрут или способ создания цифрового продукта.

VISUAL SOLUTION
Визуальный язык и комплект инструкций, позволяющий применить его к своему
проекту.

Это типы решений внутри общей экосистемы. Не нужно преждевременно создавать
сложную систему типов, если для первого этапа достаточно одного нового типа.

ProektMap уже развивается вокруг связки:
идея → кейс → архитектура → MCP → агенты → стек → деплой → монетизация.

Visual Solutions добавляют в эту карту ответ на вопрос:
«Какой визуальный путь я могу выбрать и как передать его своему AI-агенту?»

Продуктовая формула:

«Не создавай сайт с нуля. Найди визуальное решение, которое тебе нравится,
и дай его своему AI-агенту».

Короткая формула:

SEE IT. BUY IT. BUILD IT WITH AI.

============================================================
6. ЧТО ТАКОЕ DONOR
============================================================

DONOR — существующий сайт или страница, выбранная как визуальный источник.
Это сырье для исследования, а не товар и не объект буквального копирования.

Донором может быть:
- сайт студии или агентства;
- SaaS или AI-продукт;
- editorial-сайт;
- e-commerce;
- портфолио;
- архитектурный проект;
- ресторан или локальный бизнес;
- dashboard;
- экспериментальный веб-дизайн;
- другая страница с выразительным визуальным языком.

Ключевое различие:

DONOR ≠ CLONE.

Мы не строим процесс «вставь URL — скопируй сайт».
Мы строим процесс «исследуй URL — извлеки визуальные принципы — создай новое
решение».

============================================================
7. ЧТО БЕРЕМ ИЗ NORDIC BUILDER / NORDIC REFERENCE
============================================================

Nordic Reference дает нам важную философию:

REFERENCE → DESIGN DNA.

Эту идею следует перенести в ProektMap как основу Visual Factory.

Принципы, которые берем:

1. Референс — визуальный язык, а не сайт для копирования.

2. Не переносить в новый проект текст, бренд, логотип, изображения и уникальный
контент источника.

3. Разделять три слоя:
SOURCE
INTERPRETATION
INSTRUCTION.

4. DESIGN.md должен фиксировать не просто описание сайта, а правила, которые
помогают получить похожее визуальное ощущение.

5. Переходить от наблюдений по скриншоту к системе дизайн-правил.

6. Важна визуальная DNA, а не буквальная копия.

7. Агент должен прочитать DESIGN.md до начала верстки.

8. Отделять визуальную механику от предметного содержания.

Nordic Reference отвечает за извлечение визуальной системы.
ProektMap превращает эту систему в упакованное, проверенное и распространяемое
решение.

============================================================

NORDIC:

PROEKTMAP:

→ AGENT PACKAGE → USER PROJECT

Nordic помогает понять и описать визуальный язык.
ProektMap делает из этого повторяемый продуктовый процесс и библиотеку решений.

============================================================
9. DESIGN.md — ЯЗЫК МЕЖДУ РЕФЕРЕНСОМ И АГЕНТОМ
============================================================

DESIGN.md — не огромный маркетинговый prompt и не набор субъективных
прилагательных вроде «современно», «красиво» или «премиально».

Это структурированный документ о визуальной системе.

Возможная структура:

# DESIGN SYSTEM

## Design Intent
Какое визуальное ощущение и впечатление должен создавать интерфейс.

## Visual Character
Editorial, Swiss, brutalist, premium, technical, playful и т. п.

## Layout
Сетка, ширина контейнера, колонки, выравнивание, асимметрия.

## Typography
Display и body-шрифты, иерархия, размеры, начертания, line-height.

## Spacing
Вертикальный и горизонтальный ритм, плотность, принципы whitespace.

## Color
Основные цвета, акценты, контраст, фоны и правила применения.

## Image Direction
Тип изображений, пропорции, crop, обработка и роль изображений в композиции.

## Components
Hero, navigation, cards, lists, sections, footer и другие характерные элементы.

## Responsive Behaviour
Что меняется на tablet и mobile, что сохраняется, как перестраивается
иерархия.

## Motion
Scroll, hover, reveal, transitions и ограничения анимации.

## Content Rules
Какая длина текста, структура заголовков и объем контента поддерживают дизайн.

## Anti-patterns
Что агент не должен добавлять или упрощать.

## Quality Criteria
Как проверить, что реализация соответствует визуальной системе.

Структура может уточняться по мере практики, но документ должен быть полезен
агенту, который не видел исходный сайт.

============================================================
10. SOURCE / INTERPRETATION / INSTRUCTION
============================================================

Это один из ключевых принципов всей системы. Три слоя нельзя смешивать.

SOURCE — наблюдаемые факты:
- заголовок занимает примерно половину ширины;
- в верхней части страницы много свободного пространства;
- используется многоколоночная сетка;
- изображения имеют характерные пропорции;
- навигация закреплена или ведет себя определенным образом.

INTERPRETATION — объяснение дизайн-принципа:
- композиция строится вокруг editorial hierarchy;
- whitespace является активным структурным элементом;
- изображения несут основную часть визуального веса;
- асимметрия создает напряжение и направляет взгляд.

INSTRUCTION — указание агенту:
- не центрировать hero без причины;
- сохранять крупную типографическую иерархию;
- не превращать все секции в одинаковые карточки;
- сохранять асимметрию при адаптации;
- не добавлять декоративные элементы, не предусмотренные системой.

Если факт не наблюдался, агент не должен выдавать его за факт. Интерпретации
и предположения следует явно маркировать.

============================================================
11. CONTENT NEUTRALIZATION
============================================================

Перед созданием нового проекта нужно отделить визуальную систему от содержания
донора.

Удаляем или заменяем:
- тексты и уникальные формулировки;
- названия и брендинг;
- логотипы;
- фотографии и другие материалы, на которые нет прав;
- конкретные товарные данные;
- уникальные сущности исходного бизнеса.

Сохраняем и описываем:
- композицию;
- сетку;
- иерархию;
- типографику;
- spacing;
- роль изображений;
- механику компонентов;
- responsive-принципы;
- характер взаимодействий;
- общую визуальную атмосферу.

Правило:

СОХРАНЯЕМ ВИЗУАЛЬНУЮ МЕХАНИКУ, МЕНЯЕМ ПРЕДМЕТНЫЙ МИР.

============================================================
12. РОЛИ АГЕНТОВ В ПРОИЗВОДСТВЕННОМ КОНТУРЕ
============================================================

Это разделение ответственности, а не требование немедленно создавать
несколько автономных программных агентов. В Cursor роли могут быть оформлены
как отдельные инструкции, последовательные задачи или специализированные
субагенты — способ реализации нужно выбрать после изучения текущего репозитория.

DONOR ANALYST
Исследует источник, его структуру и наблюдаемые визуальные особенности.
Не строит новый сайт.

DESIGN EXTRACTOR
Преобразует анализ в DESIGN.md и систему правил.

CONTENT NEUTRALIZER
Отделяет визуальную систему от контента, бренда и специфики исходного бизнеса.

BUILDER
Создает новый самостоятельный проект на основе DESIGN.md, нового brief,
контента и выбранного стека.

VISUAL QA
Проверяет результат на соответствие дизайн-системе и фиксирует конкретные
отклонения.

REFINEMENT AGENT
Исправляет выявленные проблемы, не разрушая уже удачные части.

PACKAGER
Собирает пользовательский Solution Package.

PUBLISHER
Подготавливает данные и материалы для публикации в /resheniya.

Не нужно заставлять одного агента выполнять все этапы одним недифференцированным
запросом «сделай всё». Каждый этап должен иметь понятный вход, выход и критерии
готовности.

============================================================
13. DONOR ANALYST
============================================================

Первый этап — исследование, а не генерация.

Результат — DONOR ANALYSIS, который описывает:
- URL и тип источника;
- общую структуру страницы;
- layout и grid;
- ширину контейнера;
- типографику;
- hero;
- навигацию;
- ритм секций;
- карточки и списки;
- изображения и их роль;
- CTA;
- footer;
- responsive behavior;
- motion;
- визуальную иерархию;
- плотность;
- отличительные особенности.

Агент должен различать наблюдаемые факты и интерпретации, отмечать неизвестное
и не выдумывать детали, которых нельзя подтвердить доступными материалами.

============================================================
14. DESIGN EXTRACTOR
============================================================

Второй этап превращает анализ в DESIGN.md.

Задача — не повторить страницу, а сформировать систему правил, по которой
другой агент сможет построить новый сайт.

Критерий качества:

Если убрать из DESIGN.md название, тексты, бренд и изображения донора,
сможет ли другой агент понять визуальный язык и применить его к новой задаче?

Если нет, документ недостаточно системный и требует доработки.

============================================================
15. BUILDER AGENT И НОВЫЙ КОНТЕКСТ
============================================================

После извлечения дизайн-системы Builder получает новый brief.

Пример:

DONOR:
Architecture Studio

NEW PROJECT:
Dental Clinic

Builder получает:
- DESIGN.md;
- brief нового проекта;
- контент и сущности нового проекта;
- выбранный стек;
- технические ограничения;
- критерии качества.

Он не получает задачу «скопируй архитектурную студию».
Он получает задачу «используй эту визуальную систему как референс и создай
самостоятельный сайт стоматологии».

Это принципиально: переносится визуальный язык, а не идентичность исходного
сайта.

============================================================
16. VISUAL QA И REFINEMENT
============================================================

Готовый сайт нельзя автоматически считать пригодным к публикации.

Visual QA сравнивает результат с правилами DESIGN.md и проверяет:
- композицию;
- иерархию;
- типографику;
- whitespace;
- сетку;
- плотность;
- обработку изображений;
- адаптивность;
- motion;
- общий визуальный характер.

Результат проверки:
PASS или NEEDS REFINEMENT.

Если требуется доработка, QA должен выдать конкретные замечания и приоритеты.
Builder или Refinement Agent выполняет следующий проход. После исправлений
проверка повторяется.

Не нужно строить пользовательский маркетинг на псевдоточности вроде
«визуальное совпадение 92%». Внутренние метрики допустимы, если они полезны,
но важнее объяснить:
- что совпало;
- что потерялось;
- какие правила нарушены;
- что именно следует исправить.

Примеры полезной обратной связи:
- Hero стал слишком типовым SaaS.
- Grid потерял асимметрию.
- На mobile разрушилась визуальная иерархия.
- Все карточки стали одинаковыми и чрезмерно округлыми.
- Недостаточно whitespace.
- Изображения не поддерживают композицию.

============================================================
17. ОДИН DONOR МОЖЕТ ПОРОДИТЬ НЕСКОЛЬКО SOLUTIONS
============================================================

DONOR не равен SOLUTION.

Из одного источника можно извлечь несколько самостоятельных визуальных
направлений. Например, сайт архитектурной студии может вдохновить:
- Editorial Architecture;
- Minimal Portfolio;
- Dark Gallery;
- Swiss Project Grid.

Связь:

DONOR 1 → N VISUAL SOLUTIONS.

Это позволяет накапливать ценность исследования и постепенно формировать
библиотеку, а не привязывать один источник к одному товару.

Каждое новое решение, однако, должно иметь самостоятельный use case и
достаточно отличимую визуальную систему. Нельзя искусственно дробить один
результат на множество почти одинаковых товаров.

============================================================
18. ВНУТРЕННЯЯ БИБЛИОТЕКА DONORS
============================================================

В перспективе администратору нужна сущность DONOR со следующими данными:
- URL;
- название;
- категория;
- дата добавления;
- заметки об источнике;
- desktop screenshot;

- заметки о правах и ограничениях;
- связанные проекты;
- созданные Visual Solutions;
- текущий статус.

Возможные статусы производственного процесса:

DISCOVERED
→ ANALYZING
→ EXTRACTED
→ BUILDING
→ QA
→ REFINEMENT
→ READY
→ PUBLISHED
→ ARCHIVED

Это пока концептуальные статусы. Реальную модель данных следует согласовать
с существующей архитектурой ProektMap.

============================================================
19. РОЛЬ АДМИНИСТРАТОРА
============================================================

Администратор не должен вручную выполнять всю техническую работу.

Его роль:
1. Найти интересного донора.
2. Запустить анализ.
3. Проверить качество анализа и DESIGN.md.
4. Отсеять слабые направления.
5. При необходимости дать агенту корректировку.
6. Запустить генерацию нового проекта.
7. Проверить визуальный результат.
8. Принять или отклонить решение.
9. Опубликовать его в /resheniya.

AI выполняет исследование, структурирование, подготовку DESIGN.md, генерацию,
refinement, QA и упаковку.

Человек отвечает за вкус, отбор, качество, оригинальность и соответствие
философии ProektMap.

Это не фабрика бесконечного AI-контента. Это CURATED AI VISUAL LIBRARY.

Это не полноценный конструктор и не редактор сайта. Это proof of fit:

Эту функцию не обязательно включать в первую версию. Сначала нужно проверить
основной производственный процесс и интерес к самим решениям.

25. КУРАТОРСКИЙ ПРИНЦИП И ЗАЩИТА ОТ AI-SLOP
============================================================

Главная опасность — превратить библиотеку в склад однотипных AI-шаблонов.

Нам не нужно «1000 шаблонов, сгенерированных AI».
Нам нужны сильные, отобранные и проверенные визуальные решения.

Качество важнее количества.

Каждое опубликованное решение должно иметь:
- ясный visual character;
- понятный use case;
- самостоятельную дизайн-систему;
- качественный preview;
- проверенную адаптивность;
- рабочие agent instructions;
- пройденный QA.

ProektMap должен продавать вкус и отбор, а не количество.

ANTI-SLOP GUIDANCE

По умолчанию избегать:
- фиолетовых AI-градиентов без причины;
- одинаковых rounded cards;
- шаблонного SaaS hero;
- выдуманной статистики;
- бессмысленных floating blobs;
- бесцельного glassmorphism;
- Inter everywhere без обоснования;
- случайных анимаций;
- декоративных элементов без функции;
- одинаковой композиции для всех проектов.

Это не абсолютные запреты. Если выбранная дизайн-система требует конкретного
приема, его можно использовать. Главный принцип:

VISUAL INTENT > TREND.

35. ДОПОЛНИТЕЛЬНЫЙ ПРОИЗВОДСТВЕННЫЙ КОНТУР:

============================================================

Эта идея дополняет Visual Factory и расширяет ее от цельных визуальных решений
до отдельных воспроизводимых UI-паттернов и компонентов.

уникальные визуальные материалы, брендинг, тексты или закрытые реализации.

Задача ProektMap — сформировать собственную библиотеку компонентов и
инструкций для AI-агентов, адаптированную к русскоязычным разработчикам и
практике AI-assisted development.

Важно: это не обязательно отдельный самостоятельный сервис. Сначала следует
проверить, как каталог компонентов может стать частью существующей экосистемы
ProektMap и раздела /resheniya, не создавая дублирующую платформу.

------------------------------------------------------------
35.1. ОСНОВНАЯ ФИЛОСОФИЯ
------------------------------------------------------------

Мы строим не просто библиотеку готового кода.

Мы строим БИБЛИОТЕКУ ПРОВЕРЕННЫХ ИНСТРУКЦИЙ ДЛЯ AI-АГЕНТОВ.

Код сам по себе со временем становится все доступнее: пользователь может
попросить AI написать компонент. Ценность ProektMap — в отборе, точности
описания, проверке результата, адаптации и удобной передаче контекста агенту.

Каждая единица каталога должна отвечать на вопрос:

«Как получить этот эффект или паттерн в своем проекте, не тратя часы на
подбор формулировок и исправление типичных ошибок AI?»

Возможные типы материалов:
- отдельные UI-компоненты;
- анимированные компоненты;
- интерактивные паттерны;
- секции страниц;
- композиционные приемы;
- готовые группы компонентов;
- полноценные шаблоны страниц;
- инструкции по адаптации под конкретный стек или задачу.

Компонент может быть бесплатным или платным, но его ценность должна быть
подтверждена работающим примером и понятной инструкцией.

------------------------------------------------------------
35.2. КАРТОЧКА КОМПОНЕНТА
------------------------------------------------------------

Страница компонента должна показывать не только описание, но и результат.

Базовая структура:

1. LIVE PREVIEW
   Рабочее превью компонента. Для изолированного или потенциально небезопасного
   кода рассмотреть iframe/sandbox. Для проверенных компонентов возможно
   отображение непосредственно в приложении.

2. CODE
   Исходный код с подсветкой синтаксиса и возможностью копирования, если
   соответствующий уровень доступа это разрешает.

3. PROMPT
   Инструкция для AI-агента с кнопкой копирования.

4. DETAILS
   Назначение, ограничения, зависимости, доступность, responsive-поведение,
   особенности интеграции и варианты настройки.

5. COMPATIBILITY
   Проверенные среды и библиотеки. Не заявлять совместимость с инструментом,
   если компонент на нем не проверялся.

6. RELATED
   Связанные компоненты, skills, решения и примеры использования.

Визуальное превью — главный способ оценки. Код и prompt — способы переноса
результата в проект пользователя.

------------------------------------------------------------
35.3. КАК ПРОИЗВОДИТЬ КОМПОНЕНТЫ
------------------------------------------------------------

Производственный процесс похож на Visual Factory, но масштаб единицы меньше.

REFERENCE / IDEA
→ PATTERN ANALYSIS
→ COMPONENT SPEC
→ IMPLEMENTATION PROMPT
→ AI BUILD
→ TEST
→ REFINEMENT
→ DOCUMENTATION
→ PUBLICATION

Шаг 1. Сбор идей
Администратор сохраняет интересные UI-паттерны и визуальные приемы из
открытых источников, отмечая ссылку, дату и то, что именно привлекло внимание.

Шаг 2. Анализ паттерна
Нужно описать задачу, которую решает компонент, его поведение, состояния,
адаптивность и визуальные принципы. Не ограничиваться формулировкой
«сделай красиво».

Шаг 3. Подготовка задания агенту
Мета-промпт может помогать составить подробную инструкцию для Cursor или
другого агента. Инструкция должна включать:
- ROLE;
- TASK;
- CONTEXT;
- REQUIREMENTS;
- INTERACTIONS / STATES;
- RESPONSIVE BEHAVIOR;
- ACCESSIBILITY;
- CONSTRAINTS;
- DEPENDENCIES;
- OUTPUT FORMAT;
- ACCEPTANCE CRITERIA.

Промпт может быть на английском, если это повышает точность работы конкретного
агента. Документация для пользователя при этом должна быть понятной и доступной
на русском языке. Язык промпта следует выбирать по результатам тестирования,
а не считать английский универсально лучшим.

Шаг 4. Генерация
Агент создает компонент в изолированном тестовом окружении. Он не должен
самостоятельно добавлять лишние библиотеки или менять архитектуру проекта.

Шаг 5. Проверка
Проверяются:
- визуальное соответствие задаче;
- работа всех состояний;
- desktop и mobile;
- клавиатурная доступность;
- reduced motion;
- производительность;
- отсутствие ошибок консоли;
- корректность зависимостей;
- возможность повторного использования;
- понятность API и props.

Шаг 6. Итерация
Если результат не соответствует критериям, агент получает конкретные
замечания. Например: «анимация должна иметь пружинный характер», «края
маски должны плавно растворяться», «на узком экране элементы переходят
в вертикальную композицию». Не полагаться на абстрактное «улучши».

Шаг 7. Упаковка
Сохраняются код, инструкция, метаданные, preview, зависимости и результаты
проверки.

Шаг 8. Публикация
Материал появляется в каталоге ProektMap с категорией, тегами, описанием,
демонстрацией и уровнем доступа.

------------------------------------------------------------
35.4. МЕТАДАННЫЕ И ХРАНЕНИЕ
------------------------------------------------------------

Для компонента следует предусмотреть структурированные метаданные:
- slug;
- title;
- description;
- category;
- tags;
- component_type;
- framework;
- dependencies;
- prompt_content;
- code_content или ссылка на исходный файл;
- preview configuration;
- responsive notes;
- accessibility notes;
- license/source notes;
- tested environments;
- access level;
- version;
- created_at / updated_at.

Хранение может использовать Markdown/MDX с frontmatter либо существующую
модель данных ProektMap. Выбор должен быть сделан после аудита текущего
репозитория. Не вводить отдельную базу данных только потому, что она указана
в одном из референсных планов.

------------------------------------------------------------
35.5. СВЯЗЬ С VISUAL FACTORY
------------------------------------------------------------

Visual Factory и Component Library — не два конкурирующих продукта.
Это два масштаба одной системы знаний.

VISUAL FACTORY:
работает с целым визуальным языком, страницей или проектом.

COMPONENT LIBRARY:
работает с отдельным паттерном, секцией, анимацией или компонентом.

Оба контура используют общие принципы:
- reference — источник вдохновения, а не объект копирования;
- отделение наблюдений от интерпретаций и инструкций;
- самостоятельная реализация;
- проверка на реальном результате;
- понятные agent instructions;
- сохранение происхождения источника;
- человеческий контроль качества.

Компоненты могут входить в состав Visual Solution, а Visual Solution может
ссылаться на компоненты из библиотеки. Это позволит накапливать повторно
используемые элементы без дублирования.

------------------------------------------------------------
35.6. ИСТОЧНИКИ И ВДОХНОВЕНИЕ
------------------------------------------------------------

Для поиска идей можно исследовать:
- Awwwards;
- Godly;
- Mobbin;
- Refero;
- Land-book;
- профильные сообщества и подборки UI/UX;
- открытые библиотеки компонентов;
- ReactBits, 21st.dev, Magic UI, Aceternity, Hover.dev.

Список является ориентиром для исследования, а не утверждением о лицензиях
или разрешении на копирование материалов.

Адаптация означает:
увидеть общий паттерн → понять пользовательскую задачу → самостоятельно
спроектировать и реализовать вариант → добавить собственные свойства,
состояния, документацию и проверку.

Не копировать без разрешения:
- конкретный исходный код;
- уникальные иллюстрации, иконки и ассеты;
- брендинг, логотипы и тексты;
- материалы с ограничительной лицензией.

Общие интерфейсные идеи и принципы взаимодействия можно изучать, но конкретную
реализацию следует создавать самостоятельно и проверять лицензионные условия
используемых библиотек и зависимостей.

------------------------------------------------------------
35.7. РУССКОЯЗЫЧНАЯ АДАПТАЦИЯ
------------------------------------------------------------

Потенциальное отличие ProektMap — удобство для русскоязычного пользователя
и реального workflow с AI-агентами.

Это может включать:
- русскоязычные описания и инструкции;
- примеры для популярных стеков;
- ясные команды для Cursor и других агентов;
- рекомендации по локальным инструментам и сервисам там, где это уместно;
- способы копирования и экспорта, не привязанные к одному редактору;
- объяснение ограничений и типичных ошибок.

Не следует искусственно ограничивать библиотеку только российскими
технологиями. Основной критерий — практическая применимость для аудитории
ProektMap.

------------------------------------------------------------
35.8. МОНЕТИЗАЦИЯ КОМПОНЕНТОВ
------------------------------------------------------------

Возможная модель:
- часть компонентов доступна бесплатно;
- расширенные компоненты и полные инструкции входят в платный доступ;
- наборы компонентов и page templates могут продаваться как отдельные решения;
- подписка может давать доступ к библиотеке;
- в будущем MCP может предоставлять агентам доступ к разрешенным материалам.

Количество бесплатных компонентов, цены и тарифы не фиксировать до проверки
спроса и себестоимости поддержки.

Не обещать, что компонент «работает с первого раза» во всех агентах.
Корректнее указывать конкретные проверенные среды, версии и известные
ограничения.

------------------------------------------------------------
35.9. ПРОИЗВОДИТЕЛЬНОСТЬ И РЕАЛИСТИЧНЫЕ KPI
------------------------------------------------------------

Идея «10–15 качественных компонентов в день на одного человека с AI» может
использоваться только как гипотеза для эксперимента, а не как обещанный
показатель производительности.

Качественный компонент требует проектирования, реализации, тестирования,
документации и проверки адаптивности. Скорость зависит от сложности и
требуемого уровня качества.

На старте лучше измерять:
- время от идеи до проверенного компонента;
- долю компонентов, прошедших QA с первого раза;
- число итераций до приемки;
- количество дефектов после публикации;
- использование и копирование prompt;
- сохранения и переходы к связанным решениям;
- конверсию из preview в получение полного пакета.

Цель — найти устойчивый процесс производства качественных материалов,
а не максимизировать число опубликованных карточек.

------------------------------------------------------------
35.10. ПЛАН ИССЛЕДОВАНИЯ И РЕАЛИЗАЦИИ
------------------------------------------------------------

Предлагаемые этапы, которые Cursor-агенты должны уточнить после аудита проекта:

ЭТАП A — ИССЛЕДОВАНИЕ
- изучить текущую архитектуру ProektMap и /resheniya;
- сравнить пользовательские сценарии ReactBits, 21st.dev и других
  референсов;
- определить, что действительно нужно аудитории ProektMap;
- предложить модель интеграции без дублирования существующих разделов.

ЭТАП B — ПРОТОТИП
- подготовить несколько собственных компонентов разных типов;
- сделать живые preview;
- добавить вкладки Code и Prompt;
- проверить процесс от идеи до публикации;
- получить обратную связь от реальных пользователей.

ЭТАП C — КАТАЛОГ
- категории и поиск;
- метаданные;
- страницы компонентов;
- связанные материалы;
- бесплатный и платный доступ, если подтвержден спрос.

ЭТАП D — ИНТЕГРАЦИЯ
- связь компонентов с Visual Solutions;
- экспорт пакетов;
- позднее — MCP-доступ к каталогу.

Не считать предложенные сроки или конкретный стек обязательными до исследования
текущего проекта. Приоритет — повторное использование имеющейся инфраструктуры.

============================================================
36. ОБЩАЯ МОДЕЛЬ: VISUAL FACTORY + COMPONENT LIBRARY
============================================================

В итоге ProektMap может объединить два взаимодополняющих слоя:

VISUAL SOLUTIONS
«Как должен выглядеть мой продукт и как передать этот визуальный язык агенту?»

COMPONENTS
«Как получить конкретный UI-паттерн, анимацию или интерактивный элемент?»

Связь:

DONOR / IDEA
→ VISUAL DNA ИЛИ COMPONENT PATTERN
→ САМОСТОЯТЕЛЬНАЯ РЕАЛИЗАЦИЯ
→ QA
→ PROMPT + CODE + DOCUMENTATION
→ PROEKTMAP
→ AI AGENT
→ USER PROJECT

Общий актив ProektMap — не набор исходников, а накопленная экспертиза:
отобранные референсы, проверенные инструкции, дизайн-системы, компоненты,
примеры применения и понятные способы передать все это AI-агентам.

Ключевой принцип остается неизменным:

ИДЕИ МОЖНО НАЙТИ ВЕЗДЕ.
ЦЕННОСТЬ PROEKTMAP — В ОТБОРЕ, САМОСТОЯТЕЛЬНОЙ РЕАЛИЗАЦИИ,
ПРОВЕРКЕ, УПАКОВКЕ И ПЕРЕДАЧЕ ЗНАНИЙ AI-АГЕНТУ.

============================================================
37. ЕДИНОЕ ЯДРО: VISUAL DNA + COMPONENT DNA + AGENT KNOWLEDGE
============================================================

ЗАДАЧА ЭТОГО РАЗДЕЛА

До разработки новых каталогов, админки или MCP спроектировать общий формат
хранения визуальной экспертизы ProektMap. Это не требование немедленно
создавать отдельный движок или переписывать существующую архитектуру.
Сначала нужно изучить репозиторий и определить, как встроить модель в текущие
сущности, API и административные инструменты.

ГЛАВНЫЙ ТЕЗИС

ProektMap создает не каталог UI-компонентов, а систему накопления и передачи
визуальной экспертизы AI-агентам.

Три взаимосвязанных ядра:

1. VISUAL DNA — целостный визуальный язык продукта или сайта.
2. COMPONENT DNA — конкретные компоненты, паттерны и интерактивные решения.
3. AGENT KNOWLEDGE — правила, рецепты и инструкции, помогающие агенту
   правильно выбирать, реализовывать, адаптировать и проверять решения.

Единица реализации — компонент.
Единица дизайна — визуальная система.
Единица передачи знания — инструкция или рецепт.
AI-агент — потребитель накопленной экспертизы.

Эти сущности должны быть связаны, но не слиты в одну недифференцированную
карточку. Один компонент может использоваться в нескольких визуальных системах;
одна визуальная система может ссылаться на десятки компонентов; один рецепт
может описывать сборку целой страницы из нескольких решений.

------------------------------------------------------------
37.1. VISUAL DNA — ЯДРО ВИЗУАЛЬНОЙ СИСТЕМЫ
------------------------------------------------------------

Visual DNA описывает не только значения CSS-токенов, но и причины, правила,
ограничения и характер визуального языка.

Предлагаемый состав:
- identity: рабочее название и краткая характеристика стиля;
- design intent: какое впечатление и пользовательское поведение поддерживает
  дизайн;
- observed facts: что действительно наблюдалось в референсе;
- interpretation: выводы и гипотезы аналитика;
- tokens: цвета, типографика, интервалы, радиусы, границы, тени, сетки;
- composition: ширина контента, ритм секций, плотность, баланс, асимметрия;
- imagery: типы изображений, кадрирование, соотношения сторон, правила
  использования медиа;
- motion: характер анимации, длительность, easing, состояния и ограничения;
- responsive: правила изменения композиции на разных ширинах;
- accessibility: контраст, фокус, клавиатура, reduced motion;
- principles: позитивные правила, например «иерархия через типографику»;
- anti-patterns: чего следует избегать;
- implementation notes: применимость к стеку проекта;
- provenance: источник, дата анализа, автор, уровень уверенности и права;
- version: история изменений и совместимость.

Важно различать факт и интерпретацию. Например, «заголовок визуально крупный»
может быть наблюдением, а «дизайн намеренно создает редакционную иерархию» —
интерпретацией. Агент должен видеть эту разницу и не воспринимать гипотезу
как подтвержденный факт.

------------------------------------------------------------
37.2. COMPONENT DNA — ЯДРО КОМПОНЕНТА
------------------------------------------------------------

Компонент хранится как самостоятельная единица, пригодная для просмотра,
поиска, проверки и повторного использования.

Минимальный состав:
- id, slug, title, description;
- category и tags;
- preview и демонстрационные состояния;
- source/reference и происхождение идеи;
- собственная реализация либо четкая инструкция для генерации;
- prompt с контекстом и критериями приемки;
- dependencies и требования к окружению;
- API: props, варианты, события и точки расширения;
- states: default, hover, focus, active, disabled, loading, error и другие
  релевантные состояния;
- responsive behavior;
- accessibility и reduced-motion поведение;
- compatibility: фреймворки, CSS-подходы, версии и ограничения;
- usage examples;
- QA status и известные ограничения;
- связи с Visual DNA, решениями и рецептами;
- version, changelog, author и license/provenance.

Не каждый компонент обязан иметь все поля. Модель должна поддерживать
постепенное обогащение, но публикация требует минимального набора обязательных
данных и пройденной проверки.

------------------------------------------------------------
37.3. AGENT KNOWLEDGE — ЗНАНИЯ ДЛЯ АГЕНТА
------------------------------------------------------------

Это не просто поле prompt в карточке. В перспективе это библиотека знаний,
которые агент может получать в зависимости от задачи.

Типы знаний:
- component recipe — как реализовать конкретный компонент;
- composition recipe — как собрать секцию или страницу;
- design rules — как сохранять визуальную целостность;
- selection rules — когда выбирать компонент и когда не выбирать;
- compatibility rules — как адаптировать решение к стеку;
- QA checklist — как проверить визуальный и технический результат;
- anti-pattern — какие типовые ошибки не допускать;
- migration recipe — как перенести решение между версиями или стеками.

Рецепт должен содержать контекст, входные данные, шаги, ограничения, ожидаемый
результат и критерии приемки. Инструкции не должны обещать гарантированное
воспроизведение пиксель-в-пиксель: результат зависит от агента, окружения,
исходных данных и последующих изменений.

------------------------------------------------------------
37.4. ПРЕДЛАГАЕМАЯ СВЯЗЬ СУЩНОСТЕЙ
------------------------------------------------------------

VISUAL SOLUTION
  ├── содержит одну версию Visual DNA
  ├── ссылается на подходящие Component DNA
  ├── может включать composition recipes
  └── поставляется с агентским пакетом

COMPONENT
  ├── имеет собственную реализацию и/или prompt
  ├── связан с совместимыми Visual DNA
  ├── связан с рецептами и QA-проверками
  └── может входить в несколько решений

AGENT RECIPE
  ├── ссылается на компоненты и правила
  ├── указывает входные параметры и ограничения
  └── описывает проверяемый результат

DONOR / REFERENCE
  ├── хранит источник и заметки наблюдения
  ├── не является автоматически готовым решением
  └── может породить несколько независимых артефактов

Администратор должен иметь возможность проследить происхождение решения:
откуда взята идея, что было непосредственно наблюдено, что интерпретировано,
что реализовано самостоятельно и какие проверки пройдены.

============================================================
38. СОБСТВЕННЫЙ ФОРМАТ PROEKTMAP DESIGN DNA
============================================================

Рассмотреть единый машиночитаемый формат хранения дизайн-знаний. Рабочее
название — ProektMap Design DNA. Это концепция для исследования, а не решение
заранее вводить новый формат вместо существующих DESIGN.md, JSON или БД.

Ключевое требование: один источник знаний должен позволять формировать разные
представления для человека и инструмента:
- DESIGN.md для Cursor, Claude Code и других агентов;
- CSS variables / globals.css;
- Tailwind theme или конфигурацию;
- prompt для компонента или страницы;
- MCP-ответы и API;
- документацию и QA-чек-листы;
- экспортируемый пакет проекта.

Иллюстративный пример структуры:

 design_system:
   identity:
     name: "Editorial SaaS"
     principle: "Clarity over decoration"
   visual_language:
     density: "high"
     contrast: "strong"
     typography: "editorial"
     composition: "asymmetric_grid"
   tokens:
     spacing:
       section: 96
       content: 32
       compact: 12
     radius:
       card: 4
       button: 2
   behavior:
     motion:
       style: "subtle"
       duration: 180
       reduced_motion: true
   composition_rules:
     - "Avoid generic centered hero layouts"
     - "Use typography to establish hierarchy"
   agent_rules:
     - "Read DESIGN.md before implementation"
     - "Preserve visual identity across pages"

Это пример для обсуждения. Перед выбором YAML, JSON, Markdown frontmatter или
существующей схемы необходимо проверить текущую модель данных, миграции,
валидацию, версионирование и удобство редактирования администратором.

Формат должен поддерживать:
- schemaVersion;
- обязательные и необязательные поля;
- неизвестные поля без потери данных при импорте/экспорте;
- валидацию типов и допустимых значений;
- версионирование и changelog;
- provenance и confidence для наблюдений;
- ссылки на связанные сущности;
- экспорт в человекочитаемый Markdown;
- обратную совместимость или явные миграции.

Не следует преждевременно строить универсальный DSL. Начать с минимальной
модели, которая решает реальные сценарии ProektMap.

============================================================
39. MCP — СПОСОБ ДОСТУПА, А НЕ САМО ЯДРО
============================================================

MCP следует рассматривать как один из возможных транспортов к накопленным
знаниям, а не как фундамент всей системы.

Сначала формируется качественная структурированная база Visual DNA,
Component DNA и Agent Knowledge. После этого ее можно предоставлять через:
- Copy Prompt;
- Markdown-файлы;
- ZIP-пакеты;
- CLI;
- API;
- интеграции с редакторами;
- MCP-сервер.

Так ProektMap не привязывается к одному протоколу, редактору или поставщику
моделей. Любой новый интерфейс доступа должен использовать общий источник
данных, а не создавать отдельную копию каталога.

Потенциальные MCP-инструменты в будущем:
- search_visual_solutions — найти подходящие визуальные системы;
- get_visual_dna — получить выбранную систему и ее правила;
- search_components — найти компоненты по задаче, стеку и стилю;
- get_component — получить компонент, prompt, зависимости и состояния;
- get_recipe — получить рецепт сборки или проверки;
- get_agent_package — собрать набор инструкций под конкретную задачу.

Это гипотезы для проектирования. Имена, схемы и набор инструментов утверждать
только после проверки реальных сценариев использования.

============================================================
40. ПРИНЦИПЫ АРХИТЕКТУРЫ И ПРОИЗВОДСТВА
============================================================

1. Сначала аудит, потом новая архитектура. Повторно использовать существующие
   сущности, авторизацию, поиск, админку и систему публикации, если это разумно.
2. Не строить новый движок ради самого движка. Отдельный сервис оправдан только
   при подтвержденной необходимости.
3. Не путать исходный код с экспертизой. Ценность — в проверенной реализации,
   объяснении, правилах применения и воспроизводимости.
4. Не считать любой найденный сайт донором готового решения. Референс требует
   анализа, самостоятельной реализации, проверки прав и нейтрализации контента.
5. Сохранять границу SOURCE / INTERPRETATION / INSTRUCTION.
6. Учитывать лицензию, авторство, товарные знаки, изображения и условия
   использования исходного материала. При сомнении не публиковать заимствованный
   код или медиа; создавать независимую реализацию на основе общих принципов.
7. Не обещать агенту идеальный результат одним промптом. Давать критерии QA,
   поддерживать итерации и фиксировать известные ограничения.
8. Не оптимизировать производство под количество карточек. Приоритет — качество,
   полезность, повторное использование и сокращение итераций пользователя.
9. Поддерживать русский язык интерфейса и документации; язык самого промпта
   выбирать эмпирически для конкретной модели и задачи.
10. Все новые функции должны помогать пользователю быстрее получить рабочий
    результат в собственном проекте, а не просто увеличивать каталог.

конкретные артефакты:

A. АУДИТ ТЕКУЩЕГО PROEKTMAP

B. МОДЕЛЬ ДАННЫХ
- предложить минимальные сущности Visual DNA, Component DNA, Agent Recipe,

- показать ER-диаграмму или эквивалентную схему;
- разделить обязательные поля MVP и поля будущих версий;

C. ФОРМАТ И ЭКСПОРТ

- подготовить несколько примеров реальных артефактов, а не только абстрактную

D. АДМИНСКИЙ WORKFLOW
- описать путь от поиска донора до публикации решения;
- определить, какие шаги автоматизированы, а какие требуют решения куратора;
- показать интерфейс проверки SOURCE / INTERPRETATION / INSTRUCTION;
- предусмотреть черновик, QA, публикацию, архивирование и обновление версии.

E. ПРОВЕРКА ГИПОТЕЗЫ
- создать небольшой вертикальный срез: одна Visual Solution, несколько
  компонентов и один рецепт;
- проверить передачу пакета в Cursor или другой агент;
- измерить число итераций, дефекты, время до приемки и понятность инструкций;
- собрать обратную связь и только после этого расширять каталог.

Ожидаемый результат исследовательского этапа — короткий ADR/проектное решение,
схема данных, пример пакета и план минимальной реализации. Не начинать массовую
разработку до согласования этих результатов.

42. ИТОГОВАЯ ФОРМУЛА PROEKTMAP
============================================================

VISUAL SOLUTIONS — целостный визуальный язык продукта.
COMPONENTS — конкретные элементы и интерактивные паттерны.
AGENT KNOWLEDGE — инструкции, рецепты, правила выбора и проверки.
DESIGN DNA — общий структурированный источник визуальных знаний.
MCP / API / EXPORT — способы передать эти знания инструментам и людям.

Вместе это образует систему, в которой каждый новый проверенный компонент,
референс, рецепт и проект усиливает остальные материалы.

Идеи можно найти где угодно.
ProektMap превращает их в самостоятельные, проверенные и передаваемые знания.

Не количество компонентов определяет ценность библиотеки, а то, насколько
точно и последовательно она помогает AI-агенту создавать качественные
интерфейсы с меньшим числом итераций.

43. ОТДЕЛЬНЫЙ КАТАЛОГ VISUAL COMPONENTS & AGENT RECIPES
============================================================

ВАЖНОЕ ПРОДУКТОВОЕ РЕШЕНИЕ

Библиотека компонентов и визуальных паттернов должна быть отдельным каталогом
ProektMap, а не подразделом /resheniya и не просто дополнительным типом карточки
в каталоге готовых решений.

/resheniya и новый каталог решают разные пользовательские задачи:

/resheniya:
- пользователь выбирает целостное решение или направление для своего продукта;
- единица каталога — законченная визуальная система, страница или набор страниц;
- пользователь изучает общий визуальный язык и адаптирует его под свой проект.

Новый каталог компонентов:
- пользователь приходит за конкретным UI-элементом, паттерном, блоком, анимацией
  или агентским рецептом;
- единица каталога — самостоятельный воспроизводимый фрагмент интерфейса или
  инструкция, которую можно применить в существующем проекте;
- пользователь сначала видит результат, затем получает способ воспроизвести его
  кодом, промптом, инструкцией или пакетом для агента.

Эти каталоги могут ссылаться друг на друга, но не должны смешиваться в одну
неразличимую сущность. Визуальное решение может включать компоненты из каталога;
компонент может быть рекомендован в нескольких решениях.

43.1. ПРОДУКТОВАЯ МОДЕЛЬ: SHOW, UNDERSTAND, USE

Каталог строится вокруг трёх действий:

1. SHOW — показать работающий визуальный результат, а не только картинку,
   описание или фрагмент кода.
2. UNDERSTAND — объяснить назначение, устройство, состояния, ограничения,
   зависимости и ситуации, в которых паттерн уместен.
3. USE — дать понятный способ применить решение в проекте пользователя:
   Copy Prompt, Copy Code, установка, экспорт или Agent Skill.

Главный принцип: сначала визуальное доказательство, затем объяснение, затем
инструмент применения. Не заставлять пользователя читать длинную документацию,
чтобы понять, что именно он получит.

43.2. ТРИ ФОРМАТА ПРЕДСТАВЛЕНИЯ

Каталог должен поддерживать несколько форматов материала. Это не три разных
продукта, а три представления единой сущности с разными типами содержимого.

A. COMPONENT — отдельный компонент или анимация.
Примеры: accordion, tooltip, animated button, cursor effect, tabs, dropdown,
modal, chart, navigation menu.
Представление: интерактивный preview, краткое описание, варианты и состояния,
код/зависимости, промпт и критерии проверки.

B. BLOCK — законченный фрагмент страницы.
Примеры: bento grid, hero section, pricing table, feature showcase, testimonial
section, CTA, footer, dashboard panel.
Представление: крупный preview в контексте, переключение вариантов, responsive
поведение, состав вложенных компонентов, код/промпт и рекомендации по адаптации.

C. SKILL / RECIPE — набор правил и инструкций для агента.
Примеры: Terminal Dark, editorial SaaS, создание выразительной типографики,
проектирование анимаций, визуальная проверка страницы, рецепт сборки hero.
Представление: краткий визуальный результат или примеры «что получится»,
назначение и ограничения, содержание инструкции, установка/подключение,
версия и совместимость. Большой Skill не обязан быть одним компонентом.

В перспективе можно добавить COMPOSITION — собранную страницу или композицию
из нескольких блоков. На старте не следует усложнять модель: Composition можно
представлять как Visual Solution либо как рецепт, ссылающийся на Block.

43.3. ИНФОРМАЦИОННАЯ АРХИТЕКТУРА КАТАЛОГА

Нужен отдельный маршрут и самостоятельная навигация. Рабочее имя —
/components или /library; окончательный URL определить после аудита роутинга
и существующих разделов ProektMap.

Предлагаемая структура:

- Главная каталога: поиск, категории, подборки, новые и проверенные материалы.
- Компоненты: простые UI-элементы и интерактивные паттерны.
- Блоки: готовые секции и фрагменты страниц.
- Skills / Recipes: дизайн-инструкции и рецепты для AI-агентов.
- Страница элемента: preview, описание, варианты, инструкции и способы применения.
- Административная часть: создание, редактирование, проверка и публикация.

Категории первого уровня могут включать:
- Navigation
- Hero & Headers
- Layouts & Grids
- Cards & Content
- Forms & Inputs
- Feedback & Overlays
- Data & Charts
- Motion & Effects
- Pricing & Conversion
- Dashboard & SaaS
- Agent Skills & Recipes

Категории должны быть понятны пользователю, а не отражать внутреннюю структуру
репозитория. Один материал может иметь несколько тегов и коллекций.

43.4. СТРАНИЦА ЭЛЕМЕНТА: ВИЗУАЛЬНЫЙ ИНТЕРФЕЙС

Страница конкретного компонента/блока должна быть ближе к документации живой
библиотеки, чем к обычной статье или маркетинговой карточке.

Рекомендуемая компоновка:

1. Хлебные крошки и категория.
2. Название, краткое назначение, статус и версия.
3. Большая рабочая область Preview.
4. Переключатели: Preview / Code / Prompt / Details.
5. Контролы демонстрации: вариант, тема, размер, состояние, если применимо.
6. Copy Prompt и Copy Code как заметные действия.
7. Информация о стеке, зависимостях, доступности и адаптивности.
8. Инструкция по применению и критерии приемки.
9. Связанные элементы и подходящие Visual Solutions.
10. История версий и известные ограничения.

Для сложных блоков предусмотреть просмотр desktop/tablet/mobile. Для анимаций
пользователь должен иметь возможность повторить эффект, остановить его и увидеть
состояние reduced motion. Для интерактивных компонентов preview должен реально
реагировать на действия, а не быть статичным скриншотом.

Не копировать интерфейс референсов буквально. Изучить их информационные паттерны,
а собственную визуальную систему ProektMap выстроить согласованно с продуктом.

43.5. PROMPT — ПЕРВОКЛАССНЫЙ АРТЕФАКТ

Промпт не должен быть случайным текстом, прикреплённым к карточке. Это отдельный
версионируемый артефакт, связанный с компонентом, блоком или Skill.

Минимальная структура промпта:
- ROLE — роль агента и ожидаемый уровень самостоятельности.
- TASK — что необходимо реализовать.
- CONTEXT — назначение компонента и контекст проекта.
- VISUAL INTENT — визуальная цель и признаки правильного результата.
- REQUIREMENTS — обязательные требования.
- INTERACTIONS & STATES — поведение и состояния.
- RESPONSIVE BEHAVIOR — адаптивность.
- ACCESSIBILITY — клавиатура, семантика, контраст, reduced motion.
- STACK & DEPENDENCIES — допустимые технологии и установка.
- CONSTRAINTS — чего нельзя делать, включая анти-паттерны.
- OUTPUT FORMAT — какие файлы/изменения агент должен вернуть.
- ACCEPTANCE CRITERIA — проверяемые условия готовности.

Промпт должен учитывать контекст существующего проекта: не переустанавливать
уже имеющиеся зависимости, не заменять весь дизайн-системный слой без запроса,
сначала изучить структуру проекта и встроить решение в текущие соглашения.

Поддерживать несколько вариантов инструкции, если это оправдано:
- короткий Copy Prompt для быстрой генерации;
- подробный Prompt для более точного воспроизведения;
- Agent Skill / Recipe для повторного использования в нескольких задачах.

43.6. ПРИНЦИПЫ PREVIEW И ДЕМОНСТРАЦИИ

Preview — ключевая часть продукта. По возможности это живой изолированный пример,
а не скриншот. Он должен:
- показывать реальный компонент в рабочем состоянии;
- иметь контролируемые входные данные;
- демонстрировать основные состояния и варианты;
- не зависеть от приватных данных пользователя;
- не запускать опасные или неожиданные действия;
- быть визуально сопоставимым между версиями;
- иметь fallback, если демо не загрузилось.

Для блоков желательно показывать контекст достаточной ширины, а не сжимать
сложную композицию в маленькую карточку. Для компонентов — давать компактное
превью в каталоге и полноценную область на странице элемента.

На этапе MVP допускаются заранее подготовленные демо-страницы или статические
превью там, где живой рендер слишком дорог. Но интерфейс должен явно различать
живой preview и изображение, не создавая ложного впечатления интерактивности.

43.7. АДМИНСКОЕ ПРОИЗВОДСТВО И ПУБЛИКАЦИЯ

Администратор должен иметь возможность создать элемент без ручного изменения
кода каталога для каждой новой записи. Базовый workflow:

1. Создать черновик и выбрать тип: Component, Block или Skill/Recipe.
2. Заполнить название, slug, назначение, категории, теги и совместимость.
3. Добавить источник/референс и зафиксировать происхождение.
4. Добавить preview: изолированный пример, ссылка на демо или допустимое медиа.
5. Добавить код, промпт, инструкцию, зависимости и ограничения.
6. Проверить отображение на странице элемента и в каталоге.
7. Запустить QA: функциональность, responsive, доступность, консоль, зависимости,
   качество инструкции и права на используемые материалы.
8. Отправить на проверку, опубликовать, обновить или архивировать.

Статусы: Draft → In Review → Published → Deprecated/Archived.
Нельзя считать материал опубликованным только потому, что заполнены его поля.
Публикация требует явного подтверждения QA и проверки происхождения контента.

43.8. СВЯЗЬ С VISUAL DNA И AGENT KNOWLEDGE

Каталог не должен превращаться в склад несвязанных сниппетов. Каждый материал
может иметь связи:
- compatible_with — совместимые технологии и версии;
- requires — необходимые зависимости или базовые компоненты;
- part_of — в каких Visual Solutions используется;
- related_to — связанные компоненты и рецепты;
- derived_from — исходный референс или идея;
- tested_with — проверенные модели/агенты и контекст тестирования;
- supersedes — какая версия или запись заменена.

Visual Solution может собирать согласованный набор Blocks, Components и Skills.
Например, решение «Editorial SaaS» включает типографический Skill, несколько
блоков, набор кнопок и правила композиции. Пользователь может взять всё решение
целиком либо отдельный блок в уже существующий проект.

43.9. MVP: НЕ СТРОИТЬ СРАЗУ ОГРОМНЫЙ МАРКЕТПЛЕЙС

Первый релиз должен проверить ключевую гипотезу: помогает ли каталог быстрее
находить, понимать и внедрять визуальные паттерны через AI-агента.

Рекомендуемый вертикальный срез:
- отдельная главная каталога и страница элемента;
- три типа материалов: Component, Block, Skill/Recipe;
- поиск и базовые категории;
- живой preview хотя бы для части записей;
- Copy Prompt и Copy Code;
- минимальная админка создания/редактирования/публикации;
- связь с существующими Visual Solutions;
- аналитика действий: просмотр, копирование, переход к связанному материалу;
- тестирование нескольких материалов в реальных проектах.

Не начинать с пользовательских загрузок, рейтингов, сложной системы коллекций,
платёжного маркетплейса, публичного API или MCP. Сначала доказать полезность
базового сценария и понять, какие типы материалов реально востребованы.

43.10. МЕТРИКИ УСПЕХА

Считать не только просмотры и число записей, но и полезность:
- доля просмотров, после которых копируют Prompt или Code;
- доля скопированных материалов, реально использованных в проекте;
- время от поиска до первого рабочего результата;
- число итераций до визуальной приемки;
- доля успешных внедрений без ручной переработки;
- повторное использование компонента в других проектах;
- частота ошибок/несовместимости и скорость их исправления;
- актуальность документации и совместимость с заявленным стеком.

Количество опубликованных элементов — показатель объёма, но не основной KPI.

43.11. ЧТО ИССЛЕДОВАТЬ В РЕФЕРЕНСАХ

Изучать не только внешний вид, но и полный пользовательский путь:

- FlyonUI: документационный формат отдельного компонента, наглядный пример и
  способ переноса в проект.
- React Bits Pro Agent Kit: представление Skill как самостоятельной инструкции
  для агента с назначением, версиями, содержанием и способом установки.
- Shadcn Studio Blocks: крупное превью блока, варианты и связка с кодом/стеком.
- 21st.dev, Magic UI, TypeUI: поиск, копирование, промпты, взаимодействие с
  библиотекой и интеграционные сценарии.

Это референсы продуктовых механик, а не шаблоны для буквального копирования.
Не переносить защищённые тексты, исходный код, брендинг или платные материалы.
Фиксировать, какие идеи являются общими UX-паттернами, а какие требуют
самостоятельной реализации и проверки лицензий.

43.12. УТОЧНЕНИЕ ПРЕДЫДУЩЕЙ ФОРМУЛИРОВКИ

Фраза «решение подготавливается к публикации в /resheniya» относится только к
целостным Visual Solutions. Отдельные компоненты, блоки и Agent Skills должны
готовиться к публикации в самостоятельном каталоге компонентов/библиотеки.

Новая продуктовая схема:

/resheniya             → целостные визуальные решения
/components или /library → компоненты, блоки и рецепты для агентов
/admin                  → единый производственный контур и управление контентом
DESIGN DNA              → общий источник структурированных знаний
MCP / API / Export      → будущие каналы доставки знаний

Оба каталога используют общую экспертизу и модель связей, но сохраняют разные
сценарии, страницы, метаданные и критерии готовности.
