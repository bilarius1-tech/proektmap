# Resheniya Author

## Роль

Ты автор готового инженерного маршрута `/resheniya`. ProektMap принимает основные инженерные решения заранее; пользователь выполняет инструкции и проверяет наблюдаемый результат.

После завершения работы **не объявляй маршрут готовым к публикации**. Сначала запусти `resheniya-validator`, затем передай смысловую проверку независимому `resheniya-auditor`.

## Обязательное чтение перед работой

1. `docs/RESHENIYA-V1.md`
2. `docs/PHILOSOPHY.md`
3. Пилот-образец: `src/app/resheniya/guided-data.ts`
4. UX-образцы:
   - `src/app/resheniya/page.tsx`
   - `src/app/resheniya/saas-product/page.tsx`
   - `src/app/resheniya/saas-product/workspace/`

## Жёсткие запреты

- Не ломай и не переписывай старые Blueprint (`/blueprints`, `/[blueprint]`) без явной просьбы.
- Не смешивай `/resheniya` с `/solutions` (библиотека архитектур сообщества).
- Не создавай этапы без артефакта и без проверяемого результата.
- Не превращай `/resheniya` в курс, конструктор, анкету или proof-tracker.
- Не перекладывай на пользователя выбор основного стека, архитектуры, модели или порядка.
- Не делай Phaser/игровую оболочку ядром UX.
- Не ставь trust: verified себе — только community до аудита.
- Не деплой без `npx next build`.

## Единая модель

```text
Выбор продукта
  → Рекомендация ProektMap
    → Точная инструкция
      → Команда или готовый промпт
        → Наблюдаемый результат
          → Следующий шаг
```

Пользователь не заполняет анкету, не пишет обоснования и не выбирает основной стек. Альтернативы вторичны.

## Workflow создания нового решения

Скопируй и веди чеклист:

```text
Author Progress:
- [ ] 1. Контракт результата
- [ ] 2. Карта исполнимых шагов
- [ ] 3. Данные маршрута (data)
- [ ] 4. Страницы: каталог / обзор / workspace
- [ ] 5. Контекстные ссылки экосистемы
- [ ] 5b. Мост в Нейро каталог (/arsenal) — желательно
- [ ] 6. Mobile-first стили
- [ ] 7. Sitemap + docs
- [ ] 8. Build
- [ ] 9. Автоматический validator
- [ ] 10. Передать независимому auditor
```

### 1. Контракт результата

Зафиксируй до UI:

| Поле | Требование |
|------|------------|
| `slug` | kebab-case, уникальный, без слова `resheniya` как slug Blueprint |
| `title` | глагол результата: «Запустить…», «Создать…» |
| `result` | измеримый финиш (URL, оплата, бот в проде, заявка) |
| `duration` | реалистичный диапазон |
| `difficulty` | Лёгкий / Средний / Продвинутый |
| `audience` | кто проходит маршрут |

### 2. Карта шагов

Каждый шаг обязан иметь:

- `shortTitle` — короткое имя для сайдбара
- `goal` — наблюдаемый результат
- `recommendation` — один основной выбор ProektMap и причина
- `instructions` — точные действия и команды
- `prompt` — готовый промпт без полей анкеты
- `success` — как пользователь понимает, что получилось
- `artifact` — файл, build, commit или URL
- `terms` — glossary tooltips
- `references` — модели, программы, Skills, паттерны и промпты внутри контекста

Подробный шаблон полей: [template.md](template.md)

### 3. Файловая структура

Минимум для нового решения `slug`:

```text
src/app/resheniya/
  data.ts                          # или вынести в data/<slug>.ts + реестр
  page.tsx                         # каталог: карточка нового решения
  <slug>/
    page.tsx                       # обзор + контракт результата
    workspace/
      page.tsx
      workspace.tsx                # миссия: Понять → Решить → Сделать → Проверить
```

Пока данные статические — используй `guided-data.ts` и новый SaaS workspace. Не подключай Prisma без явной задачи.

### 4. UX-правила

- Каталог продаёт **результат**, не список уроков.
- Обзор показывает всю карту и финальный контракт.
- Workspace показывает **один текущий исполнимый шаг**.
- Пользователь не проектирует и не заполняет произвольные поля.
- Один основной путь; альтернативы только в дополнительном слое.
- Шаг содержит рекомендацию, причину, действия, команду/промпт и критерии успеха.
- Ручной путь к файлу не является основным UX. В текущем прототипе пользователь подтверждает наблюдаемый результат; затем подключается автоматическая проверка.
- На mobile ≤480/768: без horizontal overflow, CTA ≥52px, текст читаемый.
- Старую нижнюю Blueprint-панель на `/resheniya` скрывать.

### 5. Экосистема

Экосистема встраивается в инструкцию: непонятные термины — tooltip глоссария; модели — `/models`; программы — `/ai-tools`; действия агента — Skills; архитектура — patterns; готовый текст — prompts.

Не устраивай «свалку всех хабов» на каждом этапе.

### 5b. Нейро каталог (/arsenal) — желательно

Когда у решения есть явный toolkit (кодинг-агент, фото объявлений, голос, РФ-стек):

1. Прочитай skill **`arsenal-resheniya-bridge`**.
2. Добавь запись в `src/lib/arsenal/resheniya-bridges.ts` (1–3 стека + 2–4 тула + `why`).
3. На обзоре решения подключи `<ArsenalBridgePanel solutionSlug="…" />`.
4. Запрещено: пустое «см. арсенал» без конкретных slug.

Display name: **Нейро каталог**. URL: `/arsenal`.

### 6. Документация и индексы

После маршрута обнови при необходимости:

- `docs/RESHENIYA-V1.md` — если меняется модель
- `src/app/sitemap.ts` — публичные URL
- `src/components/nav/breadcrumbs.tsx` — подписи сегментов
- карту экосистемы `/sitemap`, если добавляется новый тип центра

### 7. Сдача

1. Запусти автоматическую проверку из skill **`resheniya-validator`**.
2. Исправь все блокирующие ошибки валидатора и повтори до PASS.
3. `rm -rf .next && npx next build`.
4. Кратко опиши: slug, финиш, число этапов, ключевые артефакты.
5. Передай маршрут **`resheniya-auditor`** в другой агент/сессию.

Автор, валидатор и аудитор выполняют разные роли. PASS автоматической проверки не даёт автору права пропустить независимый аудит.

## Эталон

Пилот `saas-product` — эталон качества и структуры. Новые маршруты должны быть не хуже по ясности результата и Definition of Done.
