# Visual Content Skill — ProektMap

## Главная задача

ProektMap не должен выглядеть как стена текста.

Твоя задача — превращать сложные объяснения в комбинацию:

**Текст → визуальное объяснение → пример → действие.**

Визуализация должна помогать пользователю понять материал быстрее, а не просто украшать страницу.

---

# 1. Анализируй материал перед изменениями

Перед редактированием страницы:

1. Прочитай весь материал.
2. Определи основные идеи.
3. Найди сложные, абстрактные или технические понятия.
4. Определи места, где визуальное объяснение будет эффективнее текста.
5. Для каждого такого места выбери подходящий тип визуала.

Не добавляй изображения автоматически после каждого блока текста.

---

# 2. Выбирай тип визуала

### Схема

Для архитектуры, взаимосвязей, процессов, последовательностей, структуры проекта, API, frontend/backend, базы данных, AI-агентов, MCP, workflow.

Предпочитай собственную схему, а не фотографию.

### Диаграмма

Для сравнений, количественных данных, этапов, зависимостей, распределений, роста, последовательности решений.

### UI-пример

Для дизайна интерфейсов, UX, компонентов, карточек, форм, dashboard, SaaS, мобильных интерфейсов.

Показывай конкретный интерфейс, а не абстрактную картинку.

### Фотография

Когда материал описывает реальный объект, человека, физический процесс, оборудование, место, продукт, реальный пример.

Фотография должна иметь смысловое отношение к тексту.

### Иллюстрация

Для абстрактных понятий, концепций, метафор, образовательных объяснений, ситуаций, которые сложно показать фотографией.

Предпочитай оригинальные изображения.

### Скриншот

Когда необходимо показать интерфейс программы, настройки, код, результат работы, реальный инструмент, последовательность действий.

Скриншот должен быть актуальным.

---

# 3. Правило «Сначала объясни, потом укрась»

Никогда не добавляй изображение только потому, что странице «не хватает картинок».

Каждый визуал должен отвечать хотя бы на один вопрос:

- Что это?
- Как это работает?
- Как это выглядит?
- Чем отличается?
- Что произойдёт дальше?
- Где это находится?
- Как это связано с другими элементами?
- Как сделать это самостоятельно?

Если изображение не отвечает ни на один из вопросов — не добавляй его.

---

# 4. Не используй типичный AI-сток

Избегай:

- улыбающихся людей с ноутбуками;
- абстрактных роботов;
- мозга с микросхемами;
- светящихся AI-голограмм;
- случайных 3D-объектов;
- декоративных gradient illustrations;
- generic stock photos.

Такие изображения создают ощущение AI-generated content и не помогают обучению.

---

# 5. Приоритет оригинальности

1. Собственная схема ProektMap.
2. Собственная SVG/HTML/CSS-визуализация.
3. Оригинальная AI-иллюстрация.
4. Разрешённое изображение из библиотеки с понятной лицензией.
5. Скриншот реального инструмента.
6. Внешняя фотография с проверенной лицензией.

Google, Яндекс.Картинки и Pinterest — только для поиска референсов. Не копируй случайные изображения из поисковой выдачи.

Если найдено хорошее изображение без понятной лицензии — не скачивай его для публикации. Используй как референс и предложи альтернативу.

---

# 6. Для каждой внешней картинки сохраняй источник

Если архитектура проекта позволяет, добавляй эти данные в metadata изображения.

---

# 7. Создавай визуализацию прямо внутри проекта

Если концепцию можно объяснить HTML/CSS/SVG, предпочитай этот вариант.

Преимущества: уникальность, отсутствие проблем с лицензией, адаптивность, возможность анимации, соответствие дизайну ProektMap, возможность интерактивного обучения.

---

# 8. Используй принцип «до → после»

Для практических материалов:

**До** → плохое решение → **После** → профессиональное решение

Особенно для: дизайна, UX, SEO, архитектуры, кода, AI-generated интерфейсов, типографики, структуры страницы.

---

# 9. Используй визуальные примеры из реальных проектов

Если материал говорит «Так выглядит хороший SaaS-dashboard» — покажи конкретный интерфейс или собственный пример, а не абстрактную иллюстрацию.

Формат: **объяснение → пример → разбор примера.**

---

# 10. Визуальный ритм страницы

Не создавай длинную последовательность текст-текст-текст-картинка.

Предпочтительный ритм:

**Проблема → короткое объяснение → визуализация → пример → вывод → действие.**

Большой материал можно разбивать визуальными «остановками».

---

# 11. Перед добавлением визуала спроси себя

- «Можно ли понять это быстрее, если это нарисовать?» → рисуй.
- «Нужен ли здесь реальный объект?» → ищи фотографию.
- «Нужно показать интерфейс?» → используй UI или скриншот.
- «Это процесс?» → используй workflow.
- «Это сравнение?» → используй comparison.
- «Это абстрактная идея?» → используй диаграмму, схему или оригинальную иллюстрацию.

---

# 12. Alt-текст обязателен

Плохо: alt="image"

Хорошо: alt="Схема взаимодействия frontend, API, backend и базы данных"

Описывай информацию, которую изображение передаёт, а не само изображение.

---

# 13. Не ломай существующий дизайн

Перед добавлением визуалов изучи: дизайн-систему, цвета, типографику, spacing, border-radius, карточки, тени, анимации, responsive behavior.

Новые визуалы должны выглядеть частью ProektMap. Не добавляй случайные стили.

---

# 14. Проверка после добавления

1. Не стало ли слишком много визуала?
2. Помогает ли каждый визуал пониманию?
3. Не выглядит ли страница как AI-generated landing page?
4. Не нарушена ли визуальная иерархия?
5. Хорошо ли выглядит mobile?
6. Есть ли alt?
7. Не используется ли изображение с неизвестной лицензией?
8. Не появились ли огромные изображения, замедляющие страницу?
9. Соответствует ли визуал стилю ProektMap?

---

# 15. Главный принцип ProektMap

ProektMap должен показывать не только «Что это?», но «Как это работает?» и «Как это сделать?».

Лучший материал имеет структуру:

**Понятие → Визуальное объяснение → Реальный пример → Практика → Готовый инструмент / Skill / Blueprint → Действие пользователя.**

---

# 16. Режим самостоятельного анализа

Если пользователь говорит «Сделай страницу лучше» — не ограничивайся исправлением текста.

Самостоятельно проверь: где не хватает визуального объяснения, где нужен пример, схема, скриншот, где можно заменить длинный текст визуальным блоком, где нужен интерактивный элемент.

Но **не переписывай содержание без необходимости.** Сначала сохраняй смысл материала.

---

# 17. Формат отчёта

Перед масштабными изменениями составь короткий план:

VISUAL AUDIT

1. Схема архитектуры — нужна
2. Скриншот Cursor — нужен
3. Сравнение до/после — нужно
4. Фотография — не нужна
5. Диаграмма — не нужна
6. Интерактивный пример — желательно

После этого реализуй наиболее полезные визуалы.

---

# Главный критерий

Не количество изображений.

**Количество понимания, которое получает пользователь.**

ProektMap должен выглядеть не как статья с картинками. Он должен выглядеть как **интерактивная карта знаний, которую можно увидеть, понять и применить.**
